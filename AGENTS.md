# htmlgate

A self-deployed, private-by-default HTML host: each Operator runs their own Instance in a cloud account they control. Use the vocabulary in [GLOSSARY.md](GLOSSARY.md).

## Build and test

- The Homebrew formula stays in the tap's `Formula/` directory and builds from its content-addressed `Formula/sources/<sha256>.tar`, using Homebrew's standard checksum verification and the existing checksum-pinned compiler/platform/type resources. `pnpm run cli:formula` packages the standalone CLI inputs deterministically before the release commit; regenerate after any CLI source or documentation change. Commit source, archive and formula together, run gates, tag, enforce tagged formula/archive/input checks, publish, pass required CI, deploy, then run `pnpm run cli:install` on the owner's machine. A stable tag and beta staging alias may identify the same immutable source commit without a beta package rebuild. `test/cli-release-tags.test.ts` enforces the tagged artifact whenever its tag exists and requires it in CI. Installer mutation controls never skip. `cli:install` preserves clean-tap and ancestor-only fast-forward checks, verifies the selected and tagged formula/archive/inputs, checks the linked rebuild receipt (formula revision `1`), compares installed bytes with a fresh build, runs version/help checks and requires Homebrew's CLI first on PATH. Report receipt and artifact verification separately from the version string. Preserve unrelated tap work; a rewritten release does not authorize an installer reset or force-fetch.

- `.github/workflows/release-validation.yml` runs the required gates sequentially on isolated macOS. Release validation needs the tags: checkout uses `fetch-depth: 0` and `fetch-tags: true`; in CI, an unreadable or missing tag set or formula tag fails rather than skips the formula release checks. Outside CI, unavailable tags explicitly skip those checks; with readable tags, the package's next release tag may still be absent before tagging. Conditional metadata checks live in `test/cli-release-tags.test.ts`; installer mutation controls in `test/cli-brew.test.ts` never skip. A skipped or pending mutation control is BROKEN, including mixed assertion/skip and all-skipped runs. `pnpm run mutate --check` verifies every mutation anchor without planting source; it supplements, never replaces, the full mutation gate. A runner timeout or unavailable quota blocks acceptance. Do not cancel an active mutation run or combine results from different candidates.

- Node 26 and pnpm. `pnpm install`, then `pnpm run check`: the typecheck, then every test end to end through `wrangler dev` (the real Worker, a local D1 and R2, a stand-in for the Access certs), the `htmlgate` CLI built from `packages/cli`, and the people pages in a real headless browser driven by `agent-browser`. That includes an axe WCAG 2.2 AA audit of every page in light and dark, at desktop and phone width; a page change must keep it at zero violations. The Instance's pages exist in English and pt-BR (instance.json `language`): a page change updates both strings in `src/pages.ts`, and `test/language.test.ts` covers pt-BR. DESIGN.md records the visual system.
- After any change to the gate, the headers, tokens or limits, run `pnpm run mutate`. It plants each violation and must report every one caught by an actual assertion. A timeout, startup/compile/hook error, interrupted run or missing report is BROKEN and fails the gate; a green test is MISSED. Inspect the failed test names against the planted violation. Add a mutation for a new security check. Never overlap mutations with edits or other gates.
- After a change to a page, a route or a store read, run `pnpm run bench`. Every page must load under 50 ms at p95. Load only slows pages down, so a pass on a busy host counts, but a page over budget while the host's load was 9 or more is no evidence (exit 2): run it again when the host is quieter. After a deploy, `pnpm run bench --live <instance-url>` with a token in `HTMLGATE_TOKEN` measures the pages that need no sign-in (a Public Share's page and body, not-found); gated pages need the owner's Access sign-in and are measured locally only. `pnpm run bench --site <url>` measures a deployed landing.
- After a deploy, run `pnpm run smoke <instance-url>` with a token in `HTMLGATE_TOKEN`.
- Deploy only with `pnpm run setup` (see [docs/operator.md](docs/operator.md)). It and `site:deploy` (a preview too) refuse while `src`, `site`, `migrations`, `packages/cli/src` or `scripts` hold uncommitted changes: commit first. The production Instance's config is the git-ignored `.instance/production.json`: `pnpm run setup --config .instance/production.json`. An Instance with a `domain` has its workers.dev hostname off.
- The landing at htmlgate.com is `site/`, its own Worker, never part of an Instance: `test/site.test.ts` covers it end to end, including axe in light and dark at 1280, 375 and 320 px. Deploy it only with `pnpm run site:deploy`: `--preview` (workers.dev, any time) or `--live` (htmlgate.com and www together; production, owner's OK first). Its privacy notice describes app.htmlgate.com, so deploy it only after the production Instance runs the version the notice describes. The owner's production Instance is meant to answer at https://app.htmlgate.com, where the landing's sign-in links lead.
- Tests may type JSON parsed from an HTTP response as `any` (`test/helpers.ts` and assertions on its results). Everywhere else, use `unknown` and narrow.
- Security rules the code relies on (issues #12, #13 and #18, plans 008 and 009): identity comes only from a verified `Cf-Access-Jwt-Assertion` JWT, never from `ctx.access`, a cookie or a header's presence. A ticket (`src/ticket.ts`) is not identity: the Worker issues one only after verifying that JWT, and every request under it re-checks the Allowlist and the Share. Paths are matched exactly. Every Instance response is `no-store` (the landing's are public and cacheable), and every response with a Share's HTML or any file of a site carries the sandbox CSP. An expired Share is missing on every read and write; in a multi-statement write, only the first statement decides liveness. Erasing (`POST /erase`) is the only deletion that is not soft: the Author only, from the Instance's own page (the token form's Fetch Metadata and Origin check), only the Author's own Shares, in one batch with the trash ledger.

## The repo is public

Issues, commits, branch names and docs are public. Keep the owner's email, Cloudflare account ids and Zero Trust team domain in git-ignored `.scratch/` files only. `docs/handoffs/` is git-ignored for the same reason: handoffs name local paths and account hosts, so never add one with `git add -f`.

## Reference code

The CLI in `packages/cli` is our own and follows no upstream: do not sync with, depend on or refer to another repository in its code or docs (`test/cli-own.test.ts` checks). The server code we started from has no licence file, so never take code from it. `packages/cli` began from MIT code, so `packages/cli/LICENSE` keeps that copyright and permission notice, as the licence requires; never remove it.
